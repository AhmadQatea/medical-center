1) فكرة المشروع باختصار

هذا ليس نظام SaaS متعدد العيادات. يوجد طبيب واحد فقط يملك حساب تسجيل دخول، وكل الجداول تقريباً ترتبط به عبر العمود user_id.

  • الطبيب (Doctor): يدخل عبر /login ويدير لوحة /doctor/*.
  • المريض (Patient): لا يملك حساباً. يحجز كزائر عبر /book.
رقم التواصل الحالي للعيادة (واتساب): 09594334213 — يُحفظ في config/clinic.php كمفتاح whatsapp، وفي جدول clinic_settings.whatsapp_number كمصدر الحقيقة للواجهة.

2) الطبقات المعمارية (Architecture)

المشروع يتبع ترتيباً صارماً حتى لا تختلط المسؤوليات:

1. Route — يحدد عنوان URL + HTTP Method + اسم المسار Named Route + الـ Controller.
↓
2. Controller — رفيع جداً (thin). يستقبل الطلب، يستدعي Service/Action، ويرجع View أو Redirect.
↓
3. Form Request — يتحقق من صحة المدخلات (Validation) قبل أي كتابة.
↓
4. Action — حالة استخدام كتابة واحدة (Write use-case) غالباً داخل DB::transaction.
↓
5. Service — منطق المجال المشترك (قراءة/كتابة/حساب المواعيد).
↓
6. Model (Eloquent) — يمثل جدولاً: علاقات، $fillable, casts() فقط. بدون منطق أعمال ثقيل.
↓
7. Database — الجداول الفعلية عبر Migrations.
مهم جداً للدراسة: user_id لا يوضع في $fillable. يُعيَّن عبر العلاقة مثل $doctor->clinicSetting()->firstOrCreate(...) حتى لا يستطيع أحد حقن ملكية سجل لطبيب آخر عبر النموذج.

3) دورة حياة الطلب (Request Lifecycle) — بالتفصيل الممل

تخيل أن المستخدم فتح الرابط /book أو ضغط زر «حفظ» في إعدادات العيادة. ماذا يحدث خطوة بخطوة؟

أ) طلب قراءة (GET) لعرض صفحة

  1. المتصفح يرسل HTTP GET إلى الخادم.
  2. Laravel يدخل من public/index.php ثم يبني التطبيق عبر bootstrap/app.php.
  3. يُطبَّق Middleware مجموعة web (جلسة Session، CSRF للـ POST لاحقاً، كوكيز…).
  4. موجّه التوجيه Router يطابق الـ URI مع تعريف في ملفات routes/*.php.
  5. يُستدعى Method داخل الـ Controller (مثل PublicBookingController@index).
  6. الـ Controller يطلب بيانات من Service (مثلاً إعدادات العيادة + الأيام المتاحة).
  7. الـ Service يقرأ عبر Model من Database (SQL تحت الغطاء).
  8. الـ Controller يمرر مصفوفة بيانات إلى view('booking.index', [...]).
  9. محرك Blade يترجم القالب إلى HTML.
  10. Vite يحقن ملفات CSS/JS المجمّعة (@vite).
  11. المتصفح يعرض الصفحة. إن وُجد Alpine.js يبدأ التفاعل داخل المتصفح بدون إعادة تحميل لكل نقرة.

ب) طلب كتابة (POST/PUT/DELETE)

  1. المستخدم يملأ <form> ويضغط إرسال.
  2. المتصفح يرسل الحقول + توكن _token (CSRF) + أحياناً _method لمحاكاة PUT/DELETE.
  3. Laravel يتحقق من CSRF. إن فشل → خطأ 419.
  4. إن وُجد Form Request يُنفَّذ rules(). إن فشل Validation → رجوع للصفحة مع $errors و old().
  5. عند النجاح يستدعي Controller الـ Action أو Service.
  6. Eloquent ينفّذ INSERT / UPDATE / DELETE.
  7. الـ Controller يرجع redirect()->route(...)->with('success', '...').
  8. الصفحة التالية تقرأ Flash Message وتعرضه للمستخدم.
في Laravel نستخدم غالباً Named Routes مثل route('doctor.settings.update') بدل كتابة الرابط يدوياً، حتى لا ينكسر شيء عند تغيير الـ URI.

4) ملفات الـ Routes وكيف تُسجَّل

التسجيل المركزي في bootstrap/app.php:

withRouting(
    web: routes/web.php,
    then: function () {
        Route::middleware('web')->group(routes/booking.php);
        Route::middleware('web')->group(routes/doctor.php);
        Route::middleware('web')->group(routes/auth.php);
    }
)
الملفالدورملاحظات
routes/web.php مداخل عامة / → تحويل إلى /book. /dashboard → /doctor/dashboard. مسارات Profile الخاصة بـ Breeze.
routes/booking.php حجز المريض بادئة /book وأسماء booking.*. عامة بدون auth. الـ POST مقيّد بـ throttle:10,1.
routes/doctor.php لوحة الطبيب بادئة /doctor + Middleware auth + أسماء doctor.*.
routes/auth.php تسجيل الدخول/الخروج/كلمة المرور من Laravel Breeze.

6) الـ Models والجداول — من يملك ماذا؟

كل Model في app/Models يقابل جدولاً. العلاقة الأساسية: الطبيب User هو الجذر.

User (users)
 ├── hasOne  ClinicSetting     (clinic_settings)
 ├── hasOne  ScheduleSetting   (schedule_settings)
 ├── hasMany WorkingHour       (working_hours)   // عادة 7 صفوف، weekday 0=أحد … 6=سبت
 ├── hasMany Holiday           (holidays)
 ├── hasMany Patient           (patients)        // SoftDeletes
 └── hasMany Appointment       (appointments)
        └── belongsTo Patient
Modelالجدولأهم الأعمدةدورها في التدفق
User users name, email, password حساب الطبيب للمصادقة؛ اسمه يظهر في الحجز العام وإعدادات العيادة
ClinicSetting clinic_settings clinic_name, specialty, whatsapp_number, address… هوية العيادة العامة + رقم واتساب
ScheduleSetting schedule_settings appointment_duration_minutes, break_duration_minutes, lunch_* قواعد حساب طول الموعد والفاصل والغداء
WorkingHour working_hours weekday, is_open, start_time, end_time أيام/ساعات الفتح التي تغذي صفحة /book
Holiday holidays date, title, note إغلاق يوم كامل → لا مواعيد في ذلك التاريخ
Patient patients name, phone, notes… سجل المرضى (بدون تسجيل دخول)
Appointment appointments date, start_time, end_time, status, source الموعد الفعلي؛ يُستثنى من الأوقات المتاحة إن لم يكن ملغى
قرار تصميمي مهم: لا يوجد جدول time_slots. الأوقات تُحسب وقت التشغيل في ScheduleService::availableSlots() من: ساعات العمل − الغداء − الإجازات − المواعيد المحجوزة − الأوقات الماضية لليوم الحالي.

7) مسار القراءة: من Database إلى الشاشة

القاعدة العامة للقراءة في هذا المشروع:

Browser GET
  → Route
  → Controller
  → Service::get... / list... / bookingWeeks...
  → Eloquent Model (SELECT)
  → Controller يمرر المتغيرات إلى Blade
  → HTML للمستخدم

مثال مبسّط: اسم العيادة في الشريط الجانبي للطبيب

  1. يوجد View Composer يجهّز متغيرات مشتركة مثل اسم العيادة من ClinicSetting.
  2. عند رسم layouts/doctor.blade.php تظهر هذه القيم في الـ Sidebar/Navbar دون أن يعيد كل Controller كتابتها.

مثال أدق: فتح /book

Route اسمه booking.index → PublicBookingController@index
ClinicSettingsService::primaryDoctor() يجلب أول User
ClinicSettingsService::get($doctor) يقرأ أو ينشئ صف clinic_settings
ScheduleService::bookingWeeks($doctor) يحسب أيام/أوقات هذا الأسبوع والأسبوع القادم
WhatsAppService::normalizeNumber(...) يجهّز الرقم لـ wa.me
Blade: resources/views/booking/index.blade.php يستقبل $settings, $weeks, $whatsappNumber
Alpine.js في resources/js/booking.js يدير اختيار الأسبوع/اليوم/الوقت محلياً في المتصفح

8) مسار الكتابة: من النموذج إلى Database

Browser POST/PUT/DELETE
  → Route (+ auth إن لزم)
  → Form Request (Validation)
  → Controller
  → Action و/أو Service
  → Model::create/update/delete  (SQL)
  → Redirect + flash success

الحقول داخل النموذج HTML يجب أن تطابق أسماء قواعد التحقق. مثال:

  • حقل الاسم في الإعدادات: name="clinic_name"
  • حقل واتساب في الإعدادات: name="whatsapp" ثم يُحوَّل داخل Request إلى whatsapp_number قبل الحفظ في الجدول.
  • أيام الجدول: days[0][weekday], days[0][is_open], days[0][start_time]…
نماذج Blade غالباً تستخدم مكوّنات مثل <x-form.input> و <x-ui.button> لإبقاء الواجهة موحّدة وسهلة لكبار السن (أزرار كبيرة / RTL).

9) مثال كامل 1: إعدادات العيادة (Feature مكتملة)

هذا أفضل مثال دراسي لأنه مكتمل من الواجهة حتى قاعدة البيانات مع اختبارات Pest.

أ) عرض الصفحة (قراءة)

العنصرالقيمة
URIGET /doctor/settings
Named Routedoctor.settings.index
ControllerClinicSettingsController@edit
ServiceClinicSettingsService::get($doctor)
ModelClinicSetting (+ قراءة User->name)
Viewresources/views/doctor/settings/index.blade.php

إن لم يوجد صف إعدادات بعد، firstOrCreate ينشئه بقيم افتراضية من config/clinic.php.

ب) حفظ التعديلات (كتابة)

العنصرالقيمة
URIPUT /doctor/settings
Named Routedoctor.settings.update
Formmethod="post" + @method('PUT') + @csrf
Form RequestUpdateClinicSettingsRequest
ActionUpdateClinicSettingsAction
ServiceClinicSettingsService::update
Models المتأثرةUser.name و ClinicSetting

تسلسل الحفظ حرفياً

  1. المستخدم يغيّر اسم العيادة / التخصص / واتساب… ويضغط حفظ.
  2. UpdateClinicSettingsRequest يتحقق: الحقول المطلوبة، طول النصوص، صيغة الرقم.
  3. Method clinicData() تنظّف الرقم إلى أرقام فقط وتسمّي المفتاح whatsapp_number.
  4. UpdateClinicSettingsAction::handle داخل Transaction:
    • يحدّث users.name من doctor_name.
    • يحدّث صف clinic_settings.
  5. Redirect إلى doctor.settings.index مع رسالة نجاح.
  6. أي زيارة لاحقة لـ /book ستقرأ الاسم وواتساب الجديدين من Database وليس من القيم الوهمية.

10) مثال كامل 2: إدارة الجدول (Feature مكتملة)

قراءة صفحة الجدول

  • Route: doctor.schedule.index → GET /doctor/schedule
  • Controller: ScheduleController@index
  • Service: getSettings, ensureWorkingHours (يضمن 7 أيام مغلقة افتراضياً), listHolidays
  • View: doctor/schedule/index.blade.php

حفظ أيام/ساعات/مدة الموعد

  • Route: doctor.schedule.update → PUT /doctor/schedule
  • Form Request: UpdateScheduleRequest (يتحقق من 7 أيام، أوقات البداية/النهاية، الغداء…)
  • Action: UpdateScheduleAction
  • Service: updateSettings + syncWorkingHours
  • Models: ScheduleSetting, WorkingHour

إضافة/حذف إجازة

العمليةRoute NameMethod + URIModel
إضافةdoctor.schedule.holidays.storePOST /doctor/schedule/holidaysHoliday
حذفdoctor.schedule.holidays.destroyDELETE /doctor/schedule/holidays/{holiday}Holiday

عند الحذف يتحقق الـ Controller أن $holiday->user_id يساوي الطبيب الحالي (بدل Policies في هذه المرحلة).

حتى تظهر مواعيد في /book يجب أن يفتح الطبيب يوماً واحداً على الأقل من إدارة الجدول ويحفظ. بدون ذلك تظهر رسالة: «لا توجد مواعيد متاحة».

11) مثال كامل 3: صفحة الحجز العام /book

ما الذي يُعرض؟

  1. مقدمة العيادة من ClinicSetting + اسم الطبيب من User.
  2. إن لم توجد أيام متاحة في هذا/الأسبوع القادم → مكوّن x-booking.empty-state فقط (بدون أزرار الأسابيع أو النموذج).
  3. إن وُجدت مواعيد → خطوات Alpine: أسبوع → يوم → وقت → بيانات مريض → ملخص → زر واتساب.

من أين تأتي قائمة الأيام والأوقات؟

ليست بيانات ثابتة في Blade. تُحسب في:

ScheduleService::bookingWeeks($doctor)
  → availableDaysInRange(...)
  → availableSlots($doctor, $date)
       يعتمد على WorkingHour + ScheduleSetting + Holiday + Appointment

هل يُحفظ الحجز حالياً في Database؟

مسار booking.store موجود لكنه Stub حالياً (لا يستدعي BookingService::createPublic بعد). زر واتساب يفتح https://wa.me/... من المتصفح برسالة جاهزة (اسم + يوم + وقت). حفظ الموعد كصف في جدول appointments هو الخطوة التالية المخططة في التطوير.

ملفات الواجهة ذات الصلة

  • Layout: resources/views/layouts/booking.blade.php
  • الصفحة: resources/views/booking/index.blade.php
  • مكوّنات: resources/views/components/booking/*
  • JS: resources/js/booking.js (Alpine data: bookingFlow)
  • CSS entry: resources/css/booking.css + التوكنات من app.css

12) رقم واتساب والتحويل إلى wa.me

  1. القيمة الافتراضية في الإعدادات: config('clinic.whatsapp') = 09594334213.
  2. عند إنشاء صف العيادة أول مرة تُنسخ إلى clinic_settings.whatsapp_number.
  3. الطبيب يستطيع تغييرها من /doctor/settings.
  4. WhatsAppService::normalizeNumber() يحوّل الرقم المحلي إلى صيغة دولية بدون +:
    • سوري 11 خانة يبدأ بـ 09 ← يُسبَق بـ 963
    • سعودي 10 خانات يبدأ بـ 0 ← يُسبَق بـ 966
  5. الرابط النهائي يشبه: https://wa.me/9639594334213?text=...

13) المصادقة Auth — كيف تدخل البيانات الحساسة؟

  1. الطبيب يفتح /login (Named Route: login).
  2. AuthenticatedSessionController يتحقق عبر LoginRequest (مع حد محاولات).
  3. عند النجاح تُنشأ Session وتربط المتصفح بالمستخدم User.
  4. أي Route تحت routes/doctor.php محمي بـ Middleware auth.
  5. إن زرت /doctor/dashboard بدون دخول → تحويل إلى صفحة Login.
  6. POST /logout ينهي الجلسة.
بيانات الدخول المحلية الافتراضية (من Seeder): البريد admin@gmail.com — يمكن تغييرها عبر متغيرات البيئة. لا توجد شاشة تسجيل عامة للمرضى أو لأطباء إضافيين.

14) ما هو مكتمل وما هو Stub بعد؟

الميزةالواجهةالكتابة إلى DBService
إعدادات العيادةنعمنعمClinicSettingsService مكتمل
إدارة الجدول + الإجازاتنعمنعمScheduleService مكتمل
عرض /book حسب الجدولنعمقراءة فقط + واتسابيعتمد على Schedule + Clinic
حفظ حجز المريض كموعدجزئيلا بعدBookingService::createPublic Stub
الحجز الفوري للطبيبنموذجلا بعدBookingService::createInstant Stub
قائمة المواعيد / المرضى / التايملاين / الداشبوردحالات فارغةبانتظار الربطServices أغلبها Stub للقوائم

عندما ترى في الكود throw new LogicException('Not implemented.') فهذا يعني أن التوقيع جاهز لكن المنطق لم يُكتب بعد — وهذا مقصود لبناء ميزة واحدة في كل مرة.

15) خطة دراسة مقترحة (رتّبها هكذا)

  1. اقرأ هذا الملف بالكامل مرة واحدة دون فتح الكود.
  2. افتح bootstrap/app.php ثم ملفات routes/* وطابقها مع الجدول في القسم 5.
  3. ادرس Feature إعدادات العيادة من النهاية للنهاية: View → Controller → Form Request → Action → Service → Model → Migration.
  4. ادرس Feature الجدول بنفس الأسلوب، ثم راقب أثرها على /book.
  5. افتح ScheduleService::availableSlots واتبع الحساب سطراً بسطر بقلم وورقة لتاريخ واحد.
  6. شغّل الاختبارات لترى السلوك الموثّق: php artisan test --compact --filter=ClinicSettings و --filter=Schedule و --filter=PublicBooking
  7. ارسم بنفسك مخططاً على ورقة: «زر الحفظ → أي Route → أي جدول؟»
